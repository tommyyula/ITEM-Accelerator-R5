#### D1.2.2 ITEM WMS Dynamic Form｜40 分钟

##### D1.2.2.1 现场需求不再排队：和 Agent 一起从开发到上线

**背景。**标准功能管住了收货、上架、在库、拣货、发运这些主流程。可仓库是一个现场：每个客户、每个仓库的处理方式各不相同，异常登记、状态采集、任务确认、临时看板这类差异化需求随时冒出来，过去只能排队等开发。需求从现场出发，经过实施、产品、开发、测试层层转述，每转一次，背景、痛点和优先级就淡一分；上线前现场看不到成品，上线后改一处又要等下一个迭代。

**用例。**巡检员在货架上发现一箱笔记本锂电池，外箱破了；可在系统里，它还是一箱好货。没人处理，明天它就可能被拣走、发到终端客户手里，既会引来客诉，也是安全隐患。要堵住这个口子，仓库需要三个应用：手机上的巡检上报、Web 上的派工工作台、手机上的 Move Damage 搬运任务。

**同样三个应用，两种做法（演示 s01）：**

| | 传统定制交付 | 需求方和 Agent 一起做 |
|---|---|---|
| 谁来做 | 现场 → 实施 → 产品 → 开发 → 测试，层层转述 | 需求方亲自说明，Agent 当场生成 |
| 何时见到成品 | 排进迭代、上线后才看到 | 当场试用，用真实数据验证 |
| 怎么改 | 改一处，等下一个迭代 | 哪里不对，说一句就改 |
| 谁决定上线 | 走发布排期 | 有权限的人审核后发布 |

**背后的机制。**Agent 长在 WMS 内部，懂业务本体、接口目录和 GenUI 架构，生成的东西从一开始就符合 WMS 的约定；它是用户的代理，不是超级用户，权限上限就是用户本人；做出来不等于上线，要经有权限的人审核才能发布。一句话：**Agent 理解与生成，WMS 守住规则，人来拍板。**

**演示边界。**真实：本地 WMS 中的任务类型与页面定义、主数据、权限模型（RBAC 角色＋仓库/任务归属）、数据变更日志与版本发布机制。示意：动画画面、人物与单据号。未发生：ISS 环境中的运行、生产试点和改造前基线测量。

**待补证据：**ISS 现场需求样本、现行需求交接时长与返工记录、可授权的测试环境与样例数据、数据处理批准人。

##### D1.2.2.2 演示：一箱破损电池，三个应用串起发现 → 派工 → 入坏货区

巡检员和主管各自对 Agent 说出需求，Agent 当场生成三个应用：手机端 Dynamic Task、Web 端 Dynamic Page 和一个 Dynamic Task Type。闭环的终点不是表单提交，而是有证据的业务状态变化。

| 需求方 | 说了什么 | Agent 生成了什么 | 业务结果 |
|---|---|---|---|
| 巡检员 John（手机） | “我要做库存巡检，看到破损就拍照上报” | 巡检任务页（Dynamic Task）；好用后保存为 Inventory Patrol 任务类型 | 生成 Inventory Issue，货况 Good → Damaged，这批库存不可拣 |
| 主管 Emily（Web） | “做一个破损库存转移工作台” | 破损转移工作台（Dynamic Page） | 两条 Issue 派给 Maria，创建 Move Damage 任务，Issue 变为 In Progress |
| 主管 Emily 搭建，执行人 Maria 执行（手机） | “把坏货搬到坏货区” | Move Damage 任务类型，只用一个标准步骤 Move Inventory | 库存放入 DMG-01，两条 Issue 自动 Resolved |

逐步展开：

1. **巡检上报（手机，Dynamic Task）。**John 在手持机上对 Agent 说：我要做库存巡检，看到破损就拍照上报。Agent 查阅本体里的 Inventory Issue 和上报接口，提出计划卡：扫库位、扫 LPN，自动带出客户和物料，拍照、填数量，然后上报。John 同意后任务立即创建，打开沉浸式任务页，当场就能试用。
2. **缺失信息被拦截、状态当场回写。**没拍照就提交，页面拦住并提示补齐。上报后系统创建 Inventory Issue，并把这批库存的货况从 Good 调整为 Damaged，它立刻不能再被拣货。页面清空，John 继续巡检；这个任务好用，就保存为 Inventory Patrol 任务类型，明天直接用。
3. **搭建搬运任务类型（Move Damage）。**Emily 让 Agent 把搬运做成可复用的任务类型：只用一个 composable step——Move Inventory，不写死目的库位，交给上架策略（Damaged → DMG 坏货区）。Agent 起草，Emily 试运行一遍，发布 v1。
4. **人确认与派工（Web，Dynamic Page）。**Emily 请 Agent 做破损库存转移工作台：Agent 写好取数逻辑，用真实数据预览，再起草页面。草稿只对作者开放；发布时系统根据页面会调用的每个接口算出所需权限，由 Emily 确认发布。发布后她勾选两条 Issue、选择执行人 Maria，创建 Move Damage 任务；页面以 Emily 本人身份调用接口，两条 Issue 变为 In Progress，写入记录标注来自哪个页面的哪个版本。
5. **执行（手机，Move Damage）。**Maria 在 My Tasks 收到任务。扫错库位，系统直接拒绝并提示正确位置；到 A12-05-1 扫库位、扫物料、确认数量，装进新的 To LPN；放货时系统建议 DMG-01，扫描放下，任务关闭。
6. **最终业务结果。**两条 Issue 自动变为 Resolved：Open → In Progress → Resolved，从上报到结案形成闭环。货况调整、取货和放货库存流水、页面版本和操作人全部可追溯。

**对 ISS 的启发：**三个应用都没有新建表、没有重写业务逻辑，而是用已有的对象、接口和标准步骤组合出来的；需求方自己说清楚、当场试用、当场修改。

##### D1.2.2.3 背后的机制：懂业务、守权限、用积木、先试后发

直接让 AI 写页面，常见四个问题：字段和接口对不上、权限过大、每个需求建一张新表并重写逻辑、生成即上线。做法是把这四件事都交给 WMS 已有的机制：

| 难点 | 做法 |
|---|---|
| 不懂字段与接口，看着对、跑不通 | **懂业务。**Agent 长在 WMS 内部。Item Ontology 描述业务对象、流程、规则、配置、接口与工程知识；按操作索引的接口目录和内部 Skill 告诉 Agent 该调哪个接口、权限和规则在哪里生效。目录里没有的操作不编造。 |
| Agent 权限过大，页面直查多张表 | **守权限。**Agent 是用户的代理，不是超级用户：用当前用户委托的令牌调用接口，用户能做的可以交给 Agent，用户做不了的 Agent 也做不了（角色无权限、仓库未授权、任务未指派一律拒绝）。页面取数走只读 View，在 WebAssembly 沙箱里运行；每次写入记录来自哪个页面的哪个版本。 |
| 每个需求建一张表、各自重写库存逻辑 | **用积木。**通用三层存储（Task Context · Lines · Records）承载任务数据，无需建表；常用动作封装成标准步骤（Composable Step），如 Move Inventory 封装扫描 LPN、拆分、托管、幂等和库存流水，Agent 只声明搬什么、搬到哪。 |
| 生成即上线，出错难回退 | **先试后发。**草稿 → 试运行 → 即时迭代 → 有权限的人发布；每个版本保留，可停用、可回退。 |

**GenUI 积木。**

- 四个核心概念：Dynamic Card（对话内轻量交互）、Dynamic Task（多步、现场执行的沉浸式手机任务页）、Save as Task Type（沉淀为有版本、草稿、试运行和发布的任务类型）、导入导出（测试环境导出定制包，生产环境导入一律落为草稿）。
- 通用三层存储：结构由 Agent 按场景在任务定义里声明，存为 JSON 文档、写入时校验、全程审计；业务事实仍留在所属业务对象里，任务数据只引用。
- Dynamic Page 与 Dynamic View API：Web 端调度台、审核队列、统计看板、查询工具按需生成；数据来自 TypeScript 写的只读 view 函数，整合多个现有接口、计数分组汇总后一次返回。代码按内容哈希不可变保存，在沙箱中运行：无文件系统、无环境变量、不能访问其他网络，只拿到当前用户的只读令牌。
- Custom Object：需要长期保存的客户数据（如 VAS 单）用同一套单头 / 明细 / 记录结构建模，可被多个任务引用。
- Composable Step：把反复出现的常用模块抽象成步骤。组装、补货、库位优化、坏货处理本质上都是先 Take 再 Place，都复用 Move Inventory。

**改动走版本，跨环境走定制包。**现场提出修改 → Agent 改草稿 → 试运行 → 有权限的人发布新版本；发布预览列出哪些进行中的任务将跟随新版本，它们保留已录入的结果，从最新版本继续。通常在测试环境和 Agent 一起生成、修改、试运行，导出定制包；生产环境导入一律落为草稿，再走审批和发布。

**换一个场景：复用与重验证。**可复用：本体、接口目录、三层存储、Composable Step、发布与回退机制。必须重验证：货况与上架映射、角色权限、客户数据语义、接口副作用和 Action 风险。一个任务类型通过，不能推断所有场景都通过。

以上机制在 ITEM WMS 本地环境中已实现，在 ISS 系统中能否成立需逐项验证。

##### D1.2.2.4 ISS 对标：在现有底座上，哪些需求能用积木组合出来

很多需求以前不是做不了，而是投入的人工工时太多、ROI 不够，一直排不上。底座上的业务对象、接口和常用组件齐备之后，Agent 能低成本、快速地把它们组合成应用，把数字化推进到过去覆盖不到的地方。对标不是宣布 ISS 已具备这些条件，而是逐层盘点 ISS 的底座有哪些积木、缺哪些，把缺口变成会中能回答的问题。

| 对标面 | 已知/建议检查 | Owner/会中填写 |
|---|---|---|
| 业务对象 | 核心对象、流程和规则是否成文，Agent 能否读懂并判断一个需求用到哪些对象？ | ISS Biz（team）业务 Owner：____；本体维护人：____ |
| 接口 | 常用读写操作是否都有接口、能否按操作检索？不能默认可读或可改；缺写接口的先做只读看板。 | 接口 Owner：____；COO AI Team 支撑人：____ |
| 组件 | 表单、扫码、拍照、审批、派工、看板等是否可复用？反复出现的环节是否值得沉淀为新积木？ | FDE：____；组件清单：____ |
| 权限与审计 | 能否以用户本人身份调用接口？角色、站点和任务归属能否由系统判定？写入能否追溯到人、来源页面与版本？ | 权限 Owner：____；审计位置：____ |
| 数据与样例 | 是否有授权、脱敏、可复现的测试环境与样例数据？哪些字段不能离开目标环境？ | 数据 Owner：____；批准记录：____ |
| 发布治理 | 测试/生产是否隔离？定制包导入、审批、发布、停用和回退由谁负责？ | 发布人：____；回退授权人：____ |

会中应直接追问：哪些需求因为工时投入大、ROI 不高一直没做，但用现有对象、接口和组件就能组合出来？哪些环节还靠纸面、Excel 或口头传递，适合先做一个低风险的试点？缺积木的需求缺在哪一层——对象、接口还是组件？由谁来补？哪些动作必须由人确认？谁发布、谁审批、谁授权回退？每个问题当场记下 Owner、涉及的系统/环境和证据位置。

##### D1.2.2.5 既有详细实践与边界补充

##### 验证点：代码生成与运行落在 WMS 本地环境

此处“本地”重点是基于既有 WMS 代码、业务模型和约定的本地开发/验证环境生成并验证功能，不是脱离现有软件重新搭一个通用页面。具体设备、部署位置和代码权限需按实际演示环境说明。

##### 痛点

仓库经常需要异常登记、状态采集、任务确认和临时分析页面。传统方式要反复解释需求、等待开发、联调和上线；生成一个看起来正确、却不了解 WMS 字段与接口的页面，也不能直接解决问题。

##### 解决路径

**WMS 代码 → WMS 本地环境 → 自定义页面 → 校验、测试与受控发布。**

1. 在授权范围内理解既有代码结构、字段、组件、权限、校验逻辑及接口。
2. 建立能够复现业务流程的本地验证环境和样例数据。
3. 用户用自然语言提出页面需求，生成与现有 WMS 约定一致的页面、字段和交互。
4. 补齐字段校验、角色权限、错误处理、状态更新与必要 Action。
5. 进行代码审核、构建、功能与接口测试；通过发布流程进入目标环境。

本轮演示（见 D1.2.2.2）采用库存巡检发现破损 → Web 工作台派工 → Move Damage 搬到坏货区的案例；早期设想的“仓库异常登记表单”不再作为演示场景。不能把“代码生成成功”直接当作“生产上线成功”。

##### 演示与证据

建议完整展示一次需求描述、代码生成、本地运行、业务修改、测试和状态回写。观察生成页面是否使用了正确字段、权限和接口，是否能够跟随现有软件升级。

评估开发周期、业务反复沟通次数、人工修改量、测试通过情况、上线后缺陷以及维护成本，而不只记录生成代码的速度。

##### 持续优化与 ISS 迁移

沉淀标准模板、组件、字段、Action 和测试用例，避免无限制个人定制形成新的维护负担。代码资产和业务应用分别保留版本、责任与回滚路径。

迁移到 ISS 时，首先确认现有软件和源码可用范围；需要代码、接口或跨部门系统支持时按需引入 COO AI Team。业务人员无需自己写代码，但正式发布仍需满足企业工程与安全要求。

**本节结论：**哪个 ISS 页面适合快速验证？能否取得必要代码和本地环境？生成、审核、发布及后续维护分别由谁负责？
